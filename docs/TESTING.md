# Testing

Three layers of tests, plus what was **not** tested.

## 1. Parity tests: the C core vs. the Python original

`tests/parity/` runs the untouched original (`reference/terminaltanks.py`, imported headless through
`tools/ttref.py`) and the C core (`build/host/probe`, built by `make host-tests`) on the **same seeds and inputs**
and compares the outputs as text, with floats printed by `repr` (17 significant digits) — i.e. bit-exact.

```sh
make host-tests
python3 tests/parity/run_parity.py          # world + shots
python3 tests/parity/run_ai_parity.py       # AI planning and learning
python3 tests/parity/run_battle_parity.py   # whole AI-vs-AI matches, frame by frame
```

| Test | What is compared | Last result |
|---|---|---|
| `run_parity.py` | random map (all 137), seed, wind, 2–4 tanks incl. UFO scale/hover, random designs and ammo (all 131 incl. Martyr ammo), several shots with ammo FX on/off: terrain heights, wind, tank placement, scenery draw counts, every shot's flight result, craters, damage, terrain edits | **300/300 identical** |
| `run_ai_parity.py` | AI plans for all 4 difficulties: angle, power, intended solution, P(hit), think time, status text, and the learning update after observed impacts | **24/24 identical** |
| `run_battle_parity.py` | complete matches driven at dt = 1/30 through the original `BattleScene.update` vs. `battle_update`: a snapshot (turn, wind, terrain hash, every tank's x/y/HP, the AI plan) at every AI turn and every destruction, and the round results | **6/6 matches identical** |

Notes:
* The battle test uses the host default AI budget (48 traces/frame). The DS spreads planning over more frames
  (`ai_budget` sized at run time); the plan does not depend on the budget. Re-running the battle test with a budget
  of 3 gave identical snapshots for every common prefix — the only difference was that one match had not finished
  inside the test's fixed frame count.
* **Floating-point functions.** Python takes `sin`, `cos`, `log` and `**` from the platform libm (glibc on Linux),
  and glibc is *not* correctly rounded: on 0.1–0.6 % of inputs in the game's ranges it returns the neighbouring
  double. The parity tests above use glibc, so they are bit-exact against **Python on Linux**. Python on Windows
  or macOS uses other libms and would itself differ from these numbers in the last bit now and then.
* The DS has no glibc (picolibc's functions differed from glibc on 9 of 84 probe cases). The DS build therefore
  defines `TT_XMATH` and uses `core/xmath.c`: sin, cos, log, hypot and t³ evaluated in double-double and rounded
  once, i.e. **correctly rounded**. The same parity tests run against a host build with `TT_XMATH`
  (`build/host/probe_xmath`): **world+shot 298/300, AI 24/24, battles 6/6** identical to Python; the two
  differences are a last-bit difference in the x of a shell that left the field (no gameplay effect).

## 1b. The ARM9 runs the same numbers: DS self-test ROM

`tests/ds_selftest/` compiles the parity probe into a separate ROM (`make selftest`) that runs on the emulated
ARM9 and prints its results to the debug port; `run.py` compares them with the host `probe_xmath` output.

```sh
make host-tests && python3 tests/ds_selftest/gen_cases.py 60 24 2    # 60 world, 24 AI, 2 full-battle cases
make selftest && python3 tests/ds_selftest/run.py 40000
```

Last result: **86/86 cases identical** (soft-float on the ARM9, xmath, the whole core). Together with 1. this
shows the DS simulation equals Python-on-Linux except for glibc's rounding slips (≈2 in 300 world cases).

## 2. Emulator tests: the ROM in headless melonDS

`tools/harness/harness.cpp` (built by `scripts/build_harness.sh`) runs the ROM in melonDS without a window,
presses buttons / touches the screen on given frames, saves screenshots (`.ppm`, both screens stacked) and
captures the game's debug-console output (`log_<n>.txt`). Scripts are generated by small Python files using
`tests/harness/scriptgen.py`.

```sh
python3 tests/harness/tour.py build/tour.script && build/host/harness run terminaltanks.nds build/tour.script build/tour
python3 tests/harness/battle_sp.py build/sp.script && build/host/harness run terminaltanks.nds build/sp.script build/sp
python3 tests/harness/flows.py build/fl.script && build/host/harness run terminaltanks.nds build/fl.script build/fl
python3 tests/harness/run_lan_versus.py build/lan 30          # two consoles, pass/fail
```

| Test | What it shows | Checked by |
|---|---|---|
| `tour.py` | boot, title, main menu, cheat entry on the on-screen keyboard (`iamethanlabs101` → ALL UNLOCKABLES GRANTED), and every main-menu destination: rules (1P/2P), LAN, tournament, missions, shop pages, workshop gate, how-to, tutorial, profiles, settings, links | screenshots, inspected |
| `battle_sp.py` | a single-player match vs. CPU: 14 turns, firing, AI turns, round result; `perf` lines in the log | screenshots + perf log |
| `flows.py` | tournament level 1: roadmap → loadout → whisper → battle vs. the boss, AI turns, pause menu | screenshots, inspected |
| `run_lan_versus.py` | **two consoles over emulated local wireless**: host advertises, guest scans and finds it, joins, version handshake, rules shown to the guest, start, rock-paper-scissors across the link, then alternating turns; 28 shots over 2 rounds (round end + new map) | automatic: both consoles must log the same sequence of (phase, turn, hash of terrain + HP), and every shot one side sends must arrive intact on the other — **PASS** |
| save persistence | cheat entered with an emulated SD card, emulator restarted on the same card image: the profile file `PROFILE1.SAV` exists and the unlocks are still there | manual run of `harness run … sd.img` |

Home screens and battle maps (after the first hardware test reported slow Master/Eternal screens and a laggy
Astral Rift map): cycling through all 91 home screens, every screen averages 18–37 ms a frame and every SELECT
press registered (before: 45–180 ms, with presses lost). Battle maps, one per sky-effect type (15 maps incl.
storm, tempest, inferno, aurora and Astral Rift): 18–29 ms average (Astral Rift was 330 ms, i.e. 3 fps).
Saves: legacy single-file save migrated, slot saves written and read back across emulator reboots, L+R safe start.

Performance (from the `perf` debug lines, emulated ARM9 at 67 MHz): menus 8–20 ms a frame; battle 14–20 ms
average, ≤ 40 ms while the AI plans; one-off spikes: entering a battle ≈ 75 ms (scenery bake), the first RPS
frame ≈ 340 ms (hand sprites are cached after that), round end with ~190 particles ≈ 50 ms a frame for about a
second. 30 fps is held in normal play in the emulator.

## 3. What was **not** tested

* **Real DS / DSi / 3DS hardware.** Everything above is emulator-only. melonDS is accurate for CPU timing and
  wireless at the level used here, but real radio conditions (range, interference, packet loss) were not tried;
  the transport retransmits lost packets, which the emulator did not exercise much.
* Full play-throughs of: all 20 tournament levels, all 50 missions, co-op missions over LAN, Terminal Tickets,
  the Martyr fight and its cinematics, shop purchases, building a tank in the workshop. These scenes are ported
  and rendered, and their rules are in the parity-tested core (`session.c`, `save.c`), but they were not played
  end to end in the emulator.
* Disconnect handling over LAN (quit / power off mid-match) — implemented (6 s silence or lost association →
  "CONNECTION LOST"), not exercised by a test.
* Sound beyond "it doesn't crash" (the emulator run is silent).
